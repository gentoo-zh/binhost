# 评估过但暂不做的改动

## 包体快照化（2026-08-31 评估）

### 提议

包体按世代硬链接成 `.snap-<gen>/`，索引头部写 `URI:` 把客户端钉在同一份快照上，
消除客户端获取索引后包体被删除的窗口。

### 前提都成立

- `portage/dbapi/bintree.py:1827`：`remote_base_uri = pkgindex.header.get("URI", base_url)`，
  客户端优先用头部的 `URI:`，没有才回退 `sync-uri`。
- 写入端有现成机制 `PORTAGE_BINHOST_HEADER_URI`（`bintree.py:2398`）。
- 索引里的 `PATH` 是相对路径，换掉基址就整棵树指向那一代。
- 镜像机是 xfs，硬链接实测可用，inode 剩余 1.1 亿。

### 不做的理由

**收益有限。** 清理与发布同一轮、一天一次，客户端要在取索引之后隔一整轮
（约 24 小时）后取包时才可能遇到该问题。`emerge` 的流程是 sync、解析、下载，
几分钟内完成。遇到该问题时会返回 404；重新执行 `--sync` 即可恢复。

**它导致源站与镜像行为不一致。** 四个教育网镜像主动通过 rsync 拉取我们的文件
（`rsyncd` 的 `[gentoo-zh]` module，`read only`），用什么参数由它们决定，
几乎不会带 `-H`。硬链接在源站免费，在镜像端是每代一份完整副本：实测单次拉取
630 MB 到 1.9 GB，`binpkgs` 1.6G 加 `unstable` 2.2G，两代翻倍且每轮重传。
因此不能把成本转嫁给镜像站，只能由源站写入 `URI:`，镜像不写；同一项目
会有两套路径语义，恢复流程、监控、文档和测试都需分别覆盖。

**它增加了原本不存在的失效路径。** 现在包体路径是固定的相对路径。加入
`URI:` 后，快照未建好、`URI` 配置错误或切换顺序错误，都可能导致源站用户无法取得包体；影响范围会从少数用户扩大到所有用户。

**官方未采用该机制。** Gentoo 官方 binhost 也没有 `.gen` 世代切换，
只使用 `rsync --delay-updates`，包体更新并非原子操作
（`proj/binhost.git` 的 `builders/*/binhost-update`），而它的用户量比我们
大几个数量级。这说明该窗口在实践中不是问题。

### 什么情况下重新考虑

收到实际问题报告后，再依据案例确定快照保留代数。
