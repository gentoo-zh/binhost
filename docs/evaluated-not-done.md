# 评估过但暂不做的改动

记录已经查证到底、结论是暂不实施的架构改动。避免下一个人重新走一遍，
也避免把「没做」误当成「没想到」。

## 包体快照化（2026-08-31 评估）

### 提议

包体按世代硬链接成 `.snap-<gen>/`，索引头部写 `URI:` 把客户端钉在同一份快照上，
消除「客户端拿到索引后包体被删」的窗口。

### 前提都成立

- `portage/dbapi/bintree.py:1827`：`remote_base_uri = pkgindex.header.get("URI", base_url)`，
  客户端优先用头部的 `URI:`，没有才回退 `sync-uri`。
- 写入端有现成机制 `PORTAGE_BINHOST_HEADER_URI`（`bintree.py:2398`）。
- 索引里的 `PATH` 是相对路径，换掉基址就整棵树指向那一代。
- 镜像机是 xfs，硬链接实测可用，inode 剩余 1.1 亿。

### 不做的理由

**收益薄。** 清理与发布同一轮、一天一次，客户端要在取索引之后隔一整轮
（约 24 小时）才去取包才撞得上。而 `emerge` 的流程是 sync、解析、下载，
几分钟走完。撞上的后果是 404，重新执行 `--sync` 即可，不是数据损坏。

**它让源站与镜像行为分岔。** 四个教育网镜像是它们主动 rsync 拉我们
（`rsyncd` 的 `[gentoo-zh]` module，`read only`），用什么参数由它们决定，
几乎不会带 `-H`。硬链接在源站免费，在镜像端是每代一份完整副本：实测单次拉取
630 MB 到 1.9 GB，`binpkgs` 1.6G 加 `unstable` 2.2G，两代翻倍且每轮重传。
把成本推给别人的机器不成立，于是只能源站写 `URI:`、镜像不写——同一个项目
两套路径语义，恢复流程、监控、文档、测试都要分别覆盖。

**它把一处不会出错的机制变成会出错的。** 现在包体路径是死的相对路径，错不了。加了
`URI:` 之后，快照没建好、`URI` 写错、切换顺序反了，任何一个都会让源站用户无法取得包体——从「极少数人可能 404」变成「所有人可能 404」。

**官方没有这层。** Gentoo 官方 binhost 连 `.gen` 这种世代切换都没有，
一条 `rsync --delay-updates` 就过去，包体从来没有原子性
（`proj/binhost.git` 的 `builders/*/binhost-update`），而它的用户量比我们
大几个数量级。这说明该窗口在实践中不是问题。

### 什么情况下重新考虑

有人真的报告撞上了。那时也有了真实案例来定快照要保留几代。
