# 已知并接受的风险

这里记的是查证过、决定暂不实作的项目。写在这里表示已经权衡过，不是待办事项，
也不表示已经修好。要改变某一条，把它从本文移走，并在提交里说明为什么现在值得。

## 发布不是一次完整的代际切换

`build/publish.sh` 依次做四件事：传新产物、移除不可再散布的旧产物、替换
`Packages`、替换 `Packages.gz`。这四步之间没有一个共同的切换点。

已经做掉的部分：产物先传完再换索引，所以按新索引取包不会取到还没上传的文件；
两个索引的替换带还原，第二步失败会把第一步换回去，不会长期停在一新一旧。

仍然存在的：两次 rename 之间有一个亚毫秒级的窗口，此时 `Packages` 是新的而
`Packages.gz` 是旧的。Portage 只读其中一份，不会同时比对两者，所以这个窗口对
下游没有实际后果，代价是我们自己的检查在那一瞬间可能看到不一致。

完整的解法是把每一代放进独立目录，验完之后用一次 symlink 或 rename 切换，并保留
上一代供回滚。这需要改动镜像机的目录结构与 nginx 配置，风险高于它消除的问题。

## 移除不可再散布的产物排在换索引之前

同一支脚本里，`quarantine.txt` 列出的产物在替换索引之前就从公开路径删除。因为
法律上的立即下架优先于可用性，所以这个顺序是有意的。

代价是：如果随后的索引传输失败，旧索引还指向已经删掉的文件，下游会拿到 404，
直到下一轮建置。已经做的补偿是移除失败时整轮中止；顺序本身不改。

## 建置容器能读到签名私钥

`docs/key-rotation.md` 末尾记着同一件事。建置期间私钥对容器可读，而容器要执行
上百个第三方 ebuild 的 root 阶段。要封闭这一点，得把编译与签名拆成两段，第二段
不执行任何上游代码。

## 依赖闭包不做完整解析

`build/stage-index.py` 按索引自身匹配原子，不跑 Portage 的解析器。`||` 组取第一个
索引能完整满足的分支，没有这样的分支时整组不发，并记进 `unresolved.txt`。因此
本站发布的内容不构成一份依赖完整的仓库，`build/verify-deps.py` 每天核对这一点，
站点与 README 也都写明了。
